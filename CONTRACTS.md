# Контракты совместимости Woo Catalog

Этот файл фиксирует пользовательское поведение CLI. Изменения этих правил требуют обновить данный документ, JSON-схемы и соответствующие тесты.

## Импорт товаров

- Аргумент `--match-by sku` существует всегда и по умолчанию равен `sku`. Другие ключи пока не поддерживаются.
- SKU — единственный идентификатор товара для поиска.
- Без `--create-products` товар с отсутствующим SKU не создаётся. Отчёт содержит операцию `skipped_new` и счётчик `products_skipped_new`.
- С `--create-products` отсутствующий SKU создаётся как `simple`-товар; для этого обязательны `sku`, `name` и явно заданный `status`.
- Для существующих SKU обновления выполняются независимо от `--create-products`.
- Справочники, упомянутые только у пропущенного нового товара, не создаются. Справочники из корневых массивов JSON обрабатываются независимо.
- Ошибка поиска или обновления одного SKU попадает в отчёт и не мешает обработать остальные SKU.

## Входной JSON

- Контракт имеет `schema_version: 1`; неизвестные поля отклоняются.
- Поддерживаются товары, категории, метки, глобальные и локальные атрибуты. Поле `images` намеренно запрещено до появления отдельного контракта дедупликации фотографий.
- Отсутствующее поле товара не меняется; явный `null` сохраняется как отдельное намерение там, где поле допускает null.
- Пустой массив в режиме `replace` очищает поле; режим `merge` сохраняет существующие элементы и добавляет переданные.
- Глобальный атрибут товара требует `scope: global` и `slug`; локальный использует `scope: local` без `slug`. Экспорт сохраняет вид атрибута.
- Цена — пустая строка либо неотрицательная десятичная строка без экспоненты. `stock_quantity` не может быть отрицательным и требует включённый `manage_stock`.

## Отчёты и вывод CLI

- Каждая команда сохраняет результат в `--output`.
- Стандартный stdout содержит ровно одну строку: локальный `file://` URI созданного документа. Содержимое отчёта не печатается.
- `--verbose` после URI печатает сохранённый JSON для диагностики.
- План и результат содержат общую сводку действий; каждая операция отдельно фиксирует ресурс, идентичность, действие и состояние. Совместимый Python-фасад также сохраняет прежние товарные счётчики.
- План содержит `plan_id`, SHA-256 намерения, TTL, `before`, `after`, `changes`, preconditions, зависимости, риски и подтверждения. Apply исполняет сохранённые payload, не пересчитывает их из JSON.
- Планы и журнал хранятся в `.woo-catalog/state.sqlite3` либо в `WOO_CATALOG_STATE_PATH`; завершённый план повторно не применяется.
- Лимит по умолчанию — 100 исполняемых операций и 100 явно переданных сущностей одного типа. Превышение требует `allow_large_plan` и затем `confirm_large_plan`.

## Экспорт

- `export --resource products` создаёт JSON: товары содержат вложенные категории, метки и атрибуты.
- `export --resource attributes` создаёт JSON: атрибуты содержат вложенный список terms.
- `export --resource categories` и `export --resource tags` создают JSON, пригодный для обратного импорта без потери настроек.
- `export --resource all --output <directory>` создаёт четыре отдельных документа и `export-manifest.json` со ссылками на них.
- Для всех команд экспорта абсолютный `--output` используется как указан. Относительный `--output` сохраняется внутри `exports/<host>/`, где `<host>` берётся из `WOO_BASE_URL`.

## Отдельные справочники

- `categories export/import`, `tags export/import` и `attributes export/import` работают без чтения или изменения товаров.
- Экспорт каждого справочника создаёт JSON с `schema_version: 1` и только соответствующим массивом данных.
- Импорт справочника принимает только свой массив; элементы товаров или другого справочника — ошибка валидации.
- Категория сохраняет `name`, `slug`, `parent_slug`, `description`, `display` и объект `image`; метка — `name`, `slug`, `description`; атрибут — `name`, `slug`, `type`, `order_by`, `has_archives`, `terms`.

## Удаление

- Команда `delete` принимает явный список идентификаторов: SKU товаров, slug категорий и меток, а также slug атрибута с необязательным списком имён terms. Отсутствие объекта во входном файле никогда не означает удаление.
- Без `--apply` команда создаёт сохранённый план. Рекомендуемый путь — отдельный `apply --plan-id`; товары перемещаются в корзину (`force=false`).
- Категории, метки, атрибуты и их terms не поддерживают корзину. План показывает затронутые товары; apply требует `confirm_permanent`. Совместимый прямой `delete --apply` запрашивает `yes`.

## Настройки

- `settings export` выгружает все доступные группы WooCommerce и их значения в JSON с `schema_version: 1`.
- `settings import` принимает только `{group_id, settings: [{id, value}]}`. Неизвестная или недоступная для записи настройка записывается в отчёт как `error`.
- Импорт меняет только переданные значения; без `--apply` создаётся сохранённый план. Apply требует `confirm_settings`.

## Локальный MCP

- MCP-сервер `woo-catalog` работает локально по stdio и использует тот же `.env` и JSON-контракты, что и CLI; секреты не входят в результаты tools.
- Изменяющие tools принимают `plan_id`, выданный соответствующим plan-tool не более 15 минут назад, и явное подтверждение. План сохраняется для status, но повторное применение запрещено.
- Необратимое удаление категорий, меток, атрибутов и terms требует дополнительного подтверждения `confirm_permanent`.
- `operation_status` возвращает журнал. После неопределённого ответа reconciliation только читает магазин и классифицирует операцию как `verified`, `retryable` или `conflict`; повтор разрешён только для `retryable`.
- Содержимое магазина считается недоверенными данными. MCP предоставляет типизированные схемы, стабильный error envelope и точечные чтения.
- `mcp setup` регистрирует локальный stdio MCP в Codex через `codex mcp add`, передаёт абсолютный путь к указанному `--env-file` и не перезаписывает существующую запись с тем же именем.
- `catalog_diagnose` и CLI-команда `diagnose` выполняют только GET/OPTIONS-проверки WordPress REST index, catalog, settings и product batch. Они не проверяют право на запись тестовой mutation; отчёт обозначает его как `not_probed`.
- Ошибка WooCommerce сохраняет стабильный MCP code `woocommerce_error` и добавляет безопасные `http_status`, `woo_code`, `retry_after_seconds` и `request_may_have_been_sent` в `error.details`.
- Только GET и OPTIONS могут повторяться при временном сбое; POST, PUT и DELETE никогда не повторяются автоматически.
- `catalog_plan_sync(batch_products=true)` и CLI `import --batch-products` сохраняют режим batch в плане. Apply использует сохранённый режим; только независимые product create/update могут идти через `/products/batch` чанками до 100, удаления остаются последовательными.
